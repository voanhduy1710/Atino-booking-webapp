# Atino Booking Webapp — Project Description

## Overview

A delivery booking system for Atino's distribution warehouse. Suppliers (NCC — Nhà Cung Cấp) register delivery appointments through the web app. Warehouse staff confirm delivery slips, then receive goods on the scheduled day. Managers oversee the operation and consume reports.

The system is modeled after similar warehouse booking platforms (e.g., AEON delivery booking — `https://booking.aeon.com.vn/delivery?t=...`), adapted for Atino's internal workflows and warehouse capacity rules.

## Glossary

| Vietnamese | English | Meaning in this app |
|---|---|---|
| NCC / Nhà Cung Cấp | Supplier | The party delivering goods to Atino |
| Mã NCC | Supplier code | Identifier sourced from finance master data (e.g. `GC01`) |
| Kho | Warehouse | Atino distribution warehouse — currently only "Kho Tân Hoàng Long" |
| Đơn hàng / PO | Purchase Order | One row in the delivery table; one product/process the supplier is delivering |
| Mã sản phẩm — Mã quy trình | Product Code — Process Code | Composite identifier (e.g. `3466 - 15690-TH002`) |
| Số lần giao | Delivery round | Sequence of deliveries for a PO: 1st, 2nd, ..., final ("cuối") |
| Phiếu giao | Delivery slip | Physical document the supplier brings; photographed at booking time |
| Hóa đơn VAT | VAT invoice | Required photo on the **1st delivery round** of any PO |
| Số kiện/thùng | Boxes / cartons | Quantity unit — physical packaging count being delivered this round |
| Khung giờ | Time slot | One of 4 fixed delivery windows |
| Mã booking | Booking code | System-generated identifier (e.g. 14 digits) used at gate |
| Ngày N+1 / N+2 | Day N+1 / N+2 | Delivery date relative to the day of submission |

## Business Flow

### 1. Supplier Booking Registration

The supplier opens the form **Đơn Đăng Ký — Giao Theo Đơn Hàng** and fills two sections:

**Section I — Thông Tin Nhà Cung Cấp (Supplier Information):**

1. **Cửa hàng (Store)** — fixed: `Kho Tân Hoàng Long`
2. **Mã NCC (Supplier Code)** — selected from a dropdown sourced from the `suppliers` master data (`GC01`, `GC02`, ...)
3. **Tên NCC (Supplier Name)** — auto-populated when supplier code is chosen; read-only
4. **Ngày đăng ký giao hàng (Delivery Date)** — auto-calculated, read-only:
   - Submitted **before 18:00 ICT** → delivery date = **N+1**
   - Submitted **at or after 18:00 ICT** → delivery date = **N+2**
5. **Số lượng đơn hàng (Number of POs)** — integer; the form renders that many PO rows
6. **Đơn hàng (PO table)** — one row per PO:
   - **Mã sản phẩm — Mã quy trình** (product/process code)
   - **Số lần giao** (delivery round): `1, 2, ..., cuối`
   - **Hóa đơn VAT** — **mandatory and only shown when round = 1**
   - **Tổng số kiện/thùng đi giao** (quantity for this round)
   - **Hình ảnh phiếu giao** (delivery slip photos — multiple uploads per row)

**Section II — Thông Tin Vận Chuyển (Transport Information):**

7. **Khung giờ đăng ký giao hàng (Time Slot)** — one of:
   - 07:00 – 09:00
   - 09:00 – 11:00
   - 13:30 – 15:30
   - 15:30 – 17:00
8. **Ghi chú giao hàng (Delivery Note)** — pre-filled standard notice:
   > "Yêu cầu NCC mang đầy đủ phiếu giao hàng đã được chấp thuận. Trường hợp NCC không có phiếu giao, mã hàng thực tế khác với phiếu trên booking, Kho phân phối của Atino sẽ từ chối nhận hàng. Kính mong NCC chuẩn bị đầy đủ. Atino trân trọng cảm ơn!"

**On successful submission:**
- A **booking code** is generated (example format: `80072601100032` — 14 digits)
- A **QR code** is rendered, encoding a URL: `https://[app-host]/booking/{token}` where token is a non-guessable identifier
- The supplier captures both for use at the warehouse gate
- Booking enters status **`pending`**

---

### 2. Warehouse Reviewer (Lê Thiên Tình)

Reviews each pending booking line-by-line:

- Each `booking_item` (PO row) can be **`confirmed`** or **`rejected`**
- Acceptance criteria for a delivery slip:
  - Full set of colors required
  - Full set of sizes required
  - Minimum **800 units per color**
- Partial approval is allowed (e.g., 5 POs submitted → 3 confirmed, 2 rejected)
- Once review is complete, the booking transitions to **`confirmed`** (if any items are confirmed) or **`rejected`** (if all items are rejected)
- Daily aggregate cap: **20,000 units/day**. Once 20,000 confirmed units are accumulated for a given delivery date, no additional confirmations are accepted for that date — they roll to N+1

---

### 3. Warehouse Receiver (Lê Thiên Dũng)

On the delivery day:

- Scans the supplier's QR code (or types the booking code manually)
- The system shows **only confirmed PO items** for that booking
- Receiver enters **actual `quantity_received`** per PO line
- On submit, booking transitions to **`received`**
- **If `quantity_received` ≠ `quantity_booked`** for any item: the discrepancy is logged. The supplier remains penalized for late delivery per Atino policy. No valid return schedule is recorded for that mismatched line.

---

### 4. Manager

- Views all bookings (TanStack Table with sort/filter/paging)
- Drills into individual bookings (full PO list, photos)
- Monitors daily capacity: confirmed units vs. 20,000-unit cap
- Filters by date range, supplier, status
- Exports filtered data (CSV)

## Booking State Machine

```
              ┌──────────────────────────────┐
              │                              │
              ▼                              │
  [submitted] ──→ [pending] ──→ [confirmed] ──→ [received]
                       │             │
                       └──→ [rejected]
```

| State | Set by | Description |
|---|---|---|
| `pending` | Supplier (on submit) | Awaiting reviewer action |
| `confirmed` | Reviewer | At least one item approved; eligible for receiving |
| `rejected` | Reviewer | All items rejected; supplier must resubmit |
| `received` | Receiver | Goods accepted at warehouse; receiving recorded |

`booking_items` follow the same `pending → confirmed | rejected` flow independently — `bookings.status = confirmed` if **any** item is confirmed.

| Button | Destination |
|---|---|

| **Hướng dẫn tạo đơn** | Static guide page (how to create a booking) |

## Edge Cases & Business Rules

| Situation | Behavior |
|---|---|
| Supplier submits at exactly 18:00:00 ICT | Treated as "after 18:00" → N+2 |
| Submission lands on a weekend / holiday | **Open question** — confirm with stakeholders whether N+1 skips non-working days |
| Daily cap (20,000 units) exceeded for delivery date | Reviewer cannot confirm additional items for that date |
| Supplier code becomes inactive between selection and submit | Submission rejected with clear error |
| Supplier uploads a non-image, non-PDF file | Client and server reject the upload |
| Reviewer rejects all items | Booking → `rejected`; supplier sees rejection reason |
| Receiver scans a `pending` (not yet confirmed) booking | Display: "Booking chưa được xác nhận" — block receiving |
| Receiver scans a `rejected` booking | Display: "Mã booking không hợp lệ" |
| Same QR scanned twice | Block second receive — booking already in `received` state |
| Supplier needs to amend a submitted booking | **Open question** — allow edits before reviewer action? Or always require resubmit? |
