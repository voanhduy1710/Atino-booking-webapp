# 14. Handover Rule

> **Purpose**: When ending a conversation and starting a new one, the agent writes `handover.md` in the project root so the next agent has full context to continue without re-reading the entire chat history.

---

## When to write a handover

- User says "new conversation", "handover", "switching chats", or similar
- A long session is ending and there is unfinished work
- After any major set of changes that the next agent needs to know about

---

## Output file

**Path**: `handover.md` (project root — next to `README.md`)  
**Format**: Markdown, plain English, no fluff.

---

## Required sections (in order)

### 1. Session Summary
One short paragraph. What was the overall goal of this session?

### 2. What Changed
Bullet list of every file modified/created/deleted, with a one-line description of *why*.

```
- backend/app/features/ledger/local_cache.py  — fixed theoretical balance window query
- frontend/src/shared/components/filters/DateRangePickerPopup.tsx  — new component [NEW]
- frontend/src/components/ui/DateRangePicker.tsx  — deleted (unused legacy) [DELETED]
```

### 3. What Is Currently Working
Bullet list of features that are verified working after this session's changes.

### 4. What Is Broken / Known Issues
Any bugs introduced, edge cases not handled, or things that still need fixing.  
If nothing is broken, write `None known.`

### 5. What To Work On Next
Ordered list of next tasks, most urgent first.

### 6. Key Context / Gotchas
Short bullets of non-obvious things the next agent MUST know before touching the code.  
Examples:
- "Do NOT touch the SQL view in Supabase — it has been moved to local_cache.py"
- "The `LEDGER_START_DATE` constant drives the entire balance calc; see constants.py"

### 7. Environment & How to Run
Only include if anything unusual happened (e.g. new env vars, new dependencies, port changes).  
Otherwise write `See docs/8. Development_Setup.md — no changes.`

---

## Rules for the agent writing the handover

1. **Be specific** — filename + function name, not just "the ledger file".
2. **No padding** — if a section has nothing to say, write `N/A` and move on.
3. **Git diff first** — run `git diff HEAD~1` or `git status` to get accurate file lists before writing.
4. **One truth** — if the same bug is mentioned in § 4, don't repeat it in § 5. Cross-reference instead.
5. **Keep it short** — the whole file should be under 150 lines. Next agent reads it in 60 seconds.
6. **Update, don't append** — overwrite the existing `handover.md` entirely; don't append to old content.

---

## Template (copy-paste ready)

```markdown
# Handover — [DATE]

## 1. Session Summary
[One paragraph]

## 2. What Changed
- `path/to/file.py` — reason [NEW / MODIFIED / DELETED]

## 3. What Is Currently Working
- Feature A: description

## 4. What Is Broken / Known Issues
- Bug description (file + line if known)
- OR: None known.

## 5. What To Work On Next
1. Highest priority task
2. Next task

## 6. Key Context / Gotchas
- Important non-obvious fact
- Another one

## 7. Environment & How to Run
See docs/8. Development_Setup.md — no changes.
```
