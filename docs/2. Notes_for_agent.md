## Codebase Exploration Order

1. **First:** code-review-graph MCP tools (this project has a knowledge graph)
2. **Then:** `docs/` (this folder) for intent, rules, schema
3. **Last resort:** Grep / Glob / Read

| Task | Tool to use first |
|---|---|
| Find a function or component | `mcp__code-review-graph__semantic_search_nodes` |
| Trace callers / dependencies | `mcp__code-review-graph__query_graph` |
| Understand impact of a change | `mcp__code-review-graph__get_impact_radius` |
| Review pending changes | `mcp__code-review-graph__detect_changes` + `get_review_context` |
| High-level architecture | `mcp__code-review-graph__get_architecture_overview` |
| Find tests for a function | `query_graph` with pattern `tests_for` |

Fall back to file scanning **only** when the graph doesn't cover what you need.

## Supabase Workflow

- **Project ID:** `deuuuibkqletkkbrsmxd`
- **Project URL:** `https://deuuuibkqletkkbrsmxd.supabase.co`
- All Supabase work goes through the **`supabase-mcp-server`** MCP tools.

| Need | Tool |
|---|---|
| See current schema | `list_tables` (start with `verbose: false`, then `true` for the table you care about) |
| Apply schema change | `apply_migration` — always with a descriptive name like `2026_05_create_bookings_table` |
| Generate TS types after migration | `generate_typescript_types` → write to `src/shared/types/database.ts` |
| Run a one-off query (debug) | `execute_sql` |
| Check for security issues | `get_advisors` after every migration |
| Test risky migrations | `create_branch` first, validate, then `merge_branch` |

**Rule:** Never run `execute_sql` for schema changes. Always `apply_migration` so the change is versioned.

**Rule:** After every migration, run `get_advisors` and address security/performance warnings before continuing.

## Folder Convention

```
src/
  features/
    booking/          ← supplier registration form + submission flow
    warehouse/        ← reviewer dashboard + receiver scan
    manager/          ← manager dashboard + reports
    auth/             ← staff login (suppliers don't authenticate)
  shared/
    components/       ← reusable UI primitives (Button, Input, FileUpload, etc.)
    hooks/            ← cross-feature hooks (useToast, useFileUpload)
    lib/
      supabase.ts     ← client singleton
      dateUtils.ts    ← N+1/N+2 logic, ICT-aware date helpers
      qrUtils.ts
    types/
      database.ts     ← generated from Supabase
      domain.ts       ← hand-written domain types / enums
  app/
    routes.tsx
    providers.tsx     ← QueryClient, AuthProvider, etc.
```

Each feature folder structure:
```
features/booking/
  components/         ← only used inside `booking/`
  hooks/              ← only used inside `booking/`
  services/           ← Supabase calls for this feature
  schemas.ts          ← Zod schemas
  types.ts
  index.tsx           ← the route component (page entry)
```

**Rule:** A feature does not import from another feature's internals. Cross-feature dependencies go through `shared/`.

## Where Each Business Rule Lives

| Rule | Layer | Why there |
|---|---|---|
| Delivery date N+1/N+2 | DB trigger on `bookings` | Anti-tamper; client clock can't shift dates |
| Booking code generation | DB function | Atomic with insert; uniqueness guaranteed |
| Daily 20,000-unit cap | RPC called by reviewer flow | Needs to lock + check + update atomically |
| VAT invoice required on round 1 | Check constraint on `booking_items` | DB-level guarantee |
| Supplier active check | FK + RLS | Free; comes from referential integrity |
| Time slot enum | Postgres enum | Generated into TS types |
| Booking status state machine | RLS policies + RPC `transition_booking_status` | Prevents invalid transitions client-side |

## Form Behavior Reference

**Number of POs → dynamic rows:**
- User selects N → form renders exactly N PO rows.
- Reducing N below the current count: confirm before discarding entered data on rows N+1..M.
- Increasing N: append empty rows; preserve existing.
- Implementation: `useFieldArray` from React Hook Form.

**1st delivery round → VAT invoice field:**
- Each PO row's "Số lần giao" select drives a conditional render.
- When `delivery_round === 1`: an inline `Hóa đơn VAT` upload appears in that row only.
- Switching back to round ≥ 2: hide the field and clear any uploaded reference (do not orphan the file — schedule cleanup).

**Photo upload:**
- Multiple delivery slip photos per PO row.
- Single VAT invoice file when round = 1.
- Upload starts immediately on file selection (don't wait for form submit).
- Show progress per file, allow retry on failure, allow remove before submit.

**Confirmation screen (post-submit):**
1. Large QR code (encodes booking detail URL with opaque token)
2. `Mã đăng ký: {booking_code}` displayed below
3. `Loại đăng ký: Giao theo đơn hàng (Outright)` label
4. Print-friendly layout (the supplier may print or screenshot)

## File Storage

- **Bucket:** `booking-attachments`
- **Path:** `/{booking_id}/{item_id}/{filename}` (final), or `/temp/{session_id}/{filename}` (pre-submit)
- **Bucket is private.** Generate signed URLs (`createSignedUrl`, expiry 1 hour) when serving images to the reviewer/manager UI.
- **Allowed types:** jpg, jpeg, png, pdf
- **Max size:** 10 MB per file (start here; revisit if users complain)
- On successful booking insert, a server function moves files from `/temp/...` to `/{booking_id}/{item_id}/...`
- Orphan cleanup: a scheduled Edge Function deletes `/temp/*` older than 24 hours

## Do Not Do

- Don't add features beyond what the task specifies.
- Don't introduce new dependencies without checking against the pinned stack in `1. Principal guideline.md`.
- Don't use `new Date()` for business logic without an explicit time zone — use `date-fns-tz` with `Asia/Ho_Chi_Minh`.
- Don't generate mock data in production code paths. Mocks live in tests only.
- Don't commit schema changes without an applied migration file.
- Don't hardcode supplier codes, warehouse names, or product codes in the frontend.
- Don't use raw SQL in the frontend — use the Supabase client + RPCs.
- Don't skip RLS. Every table has RLS on, with explicit policies per role.
- Don't use the service role key in any client code.
- Don't bypass server-enforced rules with client logic.
- Don't add `try/catch` to silence errors. Surface them.
- Don't write barrel files (`index.ts` re-export hubs) that hide the dependency graph.
