## Auth System

### Staff Accounts (4 fixed accounts)

Staff accounts are stored as JSON in the `VITE_STAFF_USERS` environment variable (Vite build-time). No database table for staff credentials.

```jsonc
// VITE_STAFF_USERS env var value (SHA-256 hashes — not bcrypt)
[
  { "username": "voanhduy1710", "password_hash": "<sha256>", "role": "admin",               "allowedRoutes": ["/admin", "/manager", "/reviewer", "/receiver"] },
  { "username": "lethientinh",  "password_hash": "<sha256>", "role": "warehouse_reviewer",  "allowedRoutes": ["/reviewer"] },
  { "username": "lethiendung",  "password_hash": "<sha256>", "role": "warehouse_receiver",  "allowedRoutes": ["/receiver"] },
  { "username": "lethihong",    "password_hash": "<sha256>", "role": "manager",             "allowedRoutes": ["/manager"] }
]
```

Plaintext passwords (set once, then discarded):
- `voanhduy1710` — admin password (set by developer)
- `lethientinh` / `lethiendung` / `lethihong` — initial password `123456` (staff changes on first use)

### Reserved Usernames

The 4 staff usernames (`voanhduy1710`, `lethientinh`, `lethiendung`, `lethihong`) are **blocked at the supplier registration form** via a Zod `.refine()` check. Suppliers attempting to register with these names see: `"Tên đăng nhập này không được phép sử dụng"`.

### Password Hashing

Staff passwords: hashed with **SHA-256** client-side before comparing against the hash in `VITE_STAFF_USERS`.

Supplier passwords: hashed with **SHA-256** client-side; the hash is sent to the `register_supplier` / `login_supplier` Supabase RPC.

Plaintext passwords are never stored, logged, or transmitted over the network.

### JWT

On successful login a **base64-encoded session token** is created client-side and stored in **`localStorage`**:
```jsonc
{
  "sub": "lethientinh",
  "username": "lethientinh",
  "role": "warehouse_reviewer",
  "allowedRoutes": ["/reviewer"]
  // supplier-only fields:
  // "supplier_id": "<uuid>",
  // "supplier_account_id": "<uuid>"
}
```

The token is a plain `btoa(JSON.stringify(session))` — not a signed JWT. It is used only for client-side route guarding. All sensitive DB operations are enforced by Supabase RLS and SECURITY DEFINER RPCs.

⚠️ No server-side signature verification — this is acceptable for an internal tool. If signing is needed, add a JWT_SECRET and re-sign via a server endpoint.

### RPC Error Messages

Some Supabase RPC functions return ASCII-only error strings (e.g. `"Ten dang nhap da ton tai"`). `auth.service.ts` maps these to proper Vietnamese with diacritics via `RPC_ERROR_MAP` before displaying to the user.

### Supplier Accounts

Supplier accounts are stored in the **`supplier_accounts`** Postgres table (separate from staff):

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `username` | text UNIQUE | Chosen at registration |
| `password_hash` | text | bcrypt hash |
| `full_name` | text | |
| `supplier_code_requested` | text | What they typed at registration |
| `supplier_id` | uuid FK → `suppliers` | NULL until admin approves and links |
| `status` | enum | `pending`, `active`, `rejected` |
| `reject_reason` | text | NULL unless rejected |
| `created_at` | timestamptz | |
| `approved_at` | timestamptz | |

Registration → admin approves → `status = 'active'`, `supplier_id` set → supplier can log in and submit bookings.

Supplier JWT includes their `supplier_id` so all booking queries are automatically scoped.

### Admin Page

Route `/admin` is **client-side only** — no backend guard. The route component checks that the decoded JWT has `role = 'admin'`; if not, redirects to `/login`. There is no server-side enforcement of this page (by design — internal tool only).

### `daily_capacity` (view)
```sql
CREATE VIEW daily_capacity AS
SELECT
  b.delivery_date,
  COUNT(DISTINCT b.id)                                          AS total_bookings,
  COUNT(bi.id) FILTER (WHERE bi.status = 'confirmed')           AS confirmed_items,
  SUM(bi.quantity_booked) FILTER (WHERE bi.status = 'confirmed') AS confirmed_units
FROM bookings b
JOIN booking_items bi ON bi.booking_id = b.id
GROUP BY b.delivery_date;
```

## Key DB Triggers

### `set_booking_delivery_date()` — BEFORE INSERT on `bookings`
```sql
DECLARE ict_time timestamp;
BEGIN
  ict_time := NEW.submitted_at AT TIME ZONE 'Asia/Ho_Chi_Minh';
  IF EXTRACT(HOUR FROM ict_time) < 18 THEN
    NEW.delivery_date := (ict_time::date + 1);
  ELSE
    NEW.delivery_date := (ict_time::date + 2);
  END IF;
  RETURN NEW;
END;
```

### `generate_booking_code()` — BEFORE INSERT on `bookings`
Generates `{YYYY-MM-DD}-{supplier_code}-{7-digit-random}`. Checks uniqueness; retries up to 5 times.
```sql
DECLARE
  d text;
  code_candidate text;
  supplier_code text;
BEGIN
  d := TO_CHAR(NEW.submitted_at AT TIME ZONE 'Asia/Ho_Chi_Minh', 'YYYY-MM-DD');
  SELECT s.code INTO supplier_code FROM suppliers s WHERE s.id = NEW.supplier_id;
  LOOP
    code_candidate := d || '-' || supplier_code || '-' || LPAD(FLOOR(random() * 9000000 + 1000000)::text, 7, '0');
    EXIT WHEN NOT EXISTS (SELECT 1 FROM bookings WHERE booking_code = code_candidate);
  END LOOP;
  NEW.booking_code := code_candidate;
  RETURN NEW;
END;
```

## Image Storage

### Current Setup — Google Cloud Storage

- **Bucket:** `atino-media` (project `atino-vietnam`)
- **Path prefix:** `duy_booking_images/`
- **Paths:**
  - Upload (pre-submit): `duy_booking_images/temp/{session_id}/{prefix}_{n}.{ext}`
  - Final (post-submit): `duy_booking_images/{booking_id}/{item_id}/{filename}`
- **Public read URL:** `https://storage.googleapis.com/atino-media/duy_booking_images/{path}`
- **Types stored:** delivery slip photos, VAT invoice photos, discrepancy photos
- **Format:** jpg, jpeg, png, pdf
- **Max size:** 10 MB per file

### Upload Flow

```
Browser
  │ 1. POST /functions/v1/gcs-upload  (multipart: file + path)
  ▼
gcs-upload Edge Function
  │ 2. Signs request with GCS_SERVICE_ACCOUNT_JSON
  │ 3. PUT https://storage.googleapis.com/upload/.../atino-media
  ▼
GCS bucket atino-media
  │ 4. Returns public URL to browser
  ▼
Browser stores public URL in form state
  │ 5. On submit: sends GCS URLs to finalize_booking
  ▼
finalize_booking Edge Function
     6. Inserts booking_item_photos with storage_path = public GCS URL
```

### Required GCP Setup

1. **Bucket IAM**: `allUsers` → `roles/storage.objectViewer` (public reads)
2. **Service account**: needs `roles/storage.objectAdmin` on the bucket
3. **Supabase secret**: `GCS_SERVICE_ACCOUNT_JSON` = full JSON content of service account key
   - Set via: Supabase Dashboard → Edge Functions → Secrets
4. **CORS on bucket**: allow `*` origin for PUT/POST (set via `gsutil cors set`)

### Cleanup

Temp uploads (`duy_booking_images/temp/*`) older than 24h are deleted by
the `cleanup_temp_uploads` cron Edge Function.

### Capacity Estimate

| Factor | Estimate |
|---|---|
| Bookings per day | ~20–50 |
| PO items per booking | ~3–6 average |
| Photos per PO item | ~2–3 |
| Average photo size | ~1–3 MB |
| Daily storage growth | ~0.5–2 GB/day (worst case) |
| Annual growth | ~180–730 GB/year |

Supabase Storage free tier is 1 GB; Pro plan starts at 100 GB + $0.021/GB extra. At 50 bookings/day this is manageable for the first year. Beyond that, migration to **Google Cloud Storage** is recommended (see below).

### Image Retention Policy

- **Active bookings:** retain all photos indefinitely (data is operational evidence)
- **Old bookings (> 12 months):** move to cold/archival storage (GCS Nearline/Coldline)
- Cleanup of temp uploads: hourly cron deletes `/temp/*` older than 24h
- **Supplier-deleted content:** not currently allowed in v1

### Migration Path to Google Cloud Storage

Since the app already runs on **Cloud Run**, GCS is native and cost-effective at scale. When Supabase Storage becomes a bottleneck:

1. Create a GCS bucket in the same GCP project as Cloud Run
2. Upload photos from the frontend to a Cloud Run endpoint (or a GCS signed URL generated server-side), bypassing Supabase Storage
3. Store the GCS object URL in `booking_item_photos.storage_path` (same column — no schema change)
4. Supabase `storage_path` column stores either `supabase://...` or `gcs://bucket/path` — a thin service layer resolves to a signed URL at read time

This migration can happen with zero data loss: old photos stay on Supabase Storage, new ones go to GCS. The frontend only ever receives signed URLs.

### Access Pattern

- Reviewer / manager fetching photos: Edge Function generates signed URL (Supabase) or signed URL (GCS) based on path prefix
- URLs expire after 1 hour — not stored permanently; regenerated on each view
- QR confirmation page: no photos needed

## Performance & Scale

- ~50 concurrent users — Cloud Run min-instances 1, max 3
- Pagination on every table (default 50, max 200 rows)
- No realtime in v1; reviewer dashboard polls TanStack Query every 30s
- Heavy aggregations (manager reports) use Postgres views or RPCs
- Vite build: hashed assets, long cache headers
- Image reads via signed URLs — CDN caching possible when migrating to GCS
