# Principal Guidelines

These are the binding constraints for all implementation decisions in this project.

---

## Architecture

- **Feature-based folder structure** — each major feature is a self-contained module (components, hooks, services, types). This enables safe, isolated scaling as the app grows.
- No shared "components/ui" dumping ground — reusable primitives live in `src/shared/`, feature-specific components stay inside their feature folder.
- No barrel re-exports that obscure dependency trees.

---

## Frontend

- **Framework:** React (via Vite or Next.js — TBD based on SSR need)
- **Tables:** TanStack Table (v8) for all data grids — supplier list, booking list, manager views
- **Styling:** Black and white color palette (per design mockups). Brand accent uses Atino's dark palette. No ad-hoc colors.
- **Language:** All UI text in Vietnamese. All code, variable names, comments in English.
- **Forms:** Controlled forms with validation. Dynamic PO row generation based on user-selected quantity.
- **File uploads:** Delivery slip photos and VAT invoice photos — support multiple uploads per PO row.
- **QR Code:** Generated client-side after successful booking submission. Must display booking code text below QR image.

---

## Database

- **Provider:** Supabase (PostgreSQL)
- **Project URL:** `https://deuuuibkqletkkbrsmxd.supabase.co`
- All schema changes go through Supabase MCP tools or migration files — never direct SQL edits without recording the migration.
- Use Row Level Security (RLS) from day one. Each actor (supplier, warehouse staff, manager) has distinct access policies.
- No soft deletes unless a business rule explicitly requires audit trails on deleted records.

---

## Booking Date Logic

- Submission **before 18:00** → delivery date = **N+1**
- Submission **after 18:00** → delivery date = **N+2**
- This logic must be enforced server-side (not only in the UI) to prevent manipulation.

---

## Delivery Capacity

- Warehouse confirms a maximum of **20,000 units per day**
- Once the daily cap is confirmed by the warehouse reviewer, the system opens booking slots for N+1
- Bookings that exceed daily capacity are not accepted

---

## Validation Rules

| Field | Rule |
|---|---|
| Supplier Code | Must exist in master data (validated against DB) |
| Delivery Date | Auto-calculated from submission time; not user-editable |
| Number of POs | Integer 1–99 |
| Product Code / Process Code | Free text, required |
| VAT Invoice Photo | Required on 1st delivery round only |
| Delivery Slip Photos | At least 1 photo required per PO row |
| Quantity (boxes/cartons) | Integer > 0 |
| Time Slot | Must be one of 4 predefined options |

---

## Security

- Authentication required for all roles. Suppliers authenticate with their supplier code + credentials.
- Warehouse staff and managers have separate login flows.
- File uploads must be scanned/validated (type, size limits). No executable files.
- QR codes link to read-only booking detail pages — no auth bypass via QR.

---

## Performance

- Target: ~50 concurrent users, Google Cloud Run
- No heavy client-side computation. Pagination on all tables.
- Image uploads go directly to Supabase Storage — not base64 encoded into DB.

---

## Process Rules (Non-Negotiable)

- A supplier who delivers with **incorrect quantities** relative to the booking is still penalized for late delivery.
- Warehouse staff who scan a QR code only see orders marked as **confirmed/valid** — rejected POs are not shown.
- A partially accepted booking (e.g., 3 of 5 POs confirmed) only allows the confirmed POs through — the booking code remains valid but scoped to confirmed POs only.
