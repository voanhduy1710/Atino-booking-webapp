# Principal Guidelines

Binding constraints for every implementation decision. If a requirement conflicts with these, raise it before coding.

---

## Architecture

- **Feature-based structure** — each feature is a self-contained module: `components/`, `hooks/`, `services/`, `types.ts`. New features can be added without touching unrelated ones.
- **No shared "ui" dumping ground.** Truly reusable primitives live in `src/shared/components/`. Anything used in only one feature stays inside that feature.
- **No barrel re-exports** that hide dependency trees. Import from concrete files.
- **One feature does not import from another feature's internals.** If feature A needs feature B's data, that data goes into `shared/` or is exposed via a documented service contract.

## Tech Stack (Pinned)

| Concern | Choice | Reason |
|---|---|---|
| Build tool / framework | **Vite + React 18 + TypeScript (strict)** | Fast dev loop, no SSR need (this is a logged-in operational tool, not a public marketing site) |
| Routing | **React Router v6** | Standard, no over-engineering |
| Server state | **TanStack Query v5** | Fetching, caching, mutation invalidation |
| Forms | **React Hook Form + Zod** | Schema-driven validation, dynamic field arrays for PO rows |
| Tables | **TanStack Table v8** | All data grids — bookings, suppliers, manager views |
| Styling | **Tailwind CSS** | Black/white palette only — no ad-hoc colors, no inline `style` attributes for theming |
| QR generation | **`qrcode.react`** | Client-side rendering after submit |
| QR scanning | **`@zxing/browser`** or **`html5-qrcode`** | Camera-based scan in receiver flow |
| Database / Auth / Storage | **Supabase** | Single backend — Postgres, Auth (email + password / magic link), Storage |
| Hosting | **Google Cloud Run** | Containerized; min instances 0 or 1, max ~3 |
| Testing | **Vitest + React Testing Library** (unit), **Playwright** (smoke E2E for the booking flow) | Match Vite tooling; Playwright covers the form-to-QR critical path |

No alternatives without a written reason. No additional state libraries (Redux, Zustand) unless TanStack Query + React state proves insufficient.

## Frontend Rules

- **Vietnamese UI. English code.** All user-visible strings are Vietnamese. All identifiers, comments, commit messages are English.
- **No hardcoded supplier codes, warehouse names, or product codes** in frontend code — these come from the DB.
- **Forms are server-validated.** Client-side validation is UX; server is truth.
- **Dynamic PO rows** are field arrays via React Hook Form (`useFieldArray`). Adding/removing rows must not lose previously entered data unless explicitly cleared.
- **The 1st-round VAT invoice field appears inline within its PO row** — it is not a separate section.
- **Photos upload as the user picks them**, to a temp storage path, with progress feedback. On submit, temp paths are reassigned to the final booking. On cancel/abandon, temp uploads are eligible for cleanup (scheduled job).
- **No inline `<style>` blocks.** No CSS-in-JS. Tailwind only.
- **Time zone:** all date math uses `Asia/Ho_Chi_Minh`. Use `date-fns-tz` or equivalent — never `new Date()` without an explicit zone for business logic.

---

## Database Rules

- **Provider:** Supabase Postgres at `https://deuuuibkqletkkbrsmxd.supabase.co`
- **All schema changes go through migration files** committed to the repo, applied via `mcp__supabase-mcp-server__apply_migration`. No undocumented dashboard edits.
- **RLS is enabled on every table from day one.** No table is exposed without a written RLS policy per role.
- **Foreign keys are explicit and indexed.** No orphan rows.
- **Enums are Postgres enums** — not check constraints on text — so type generation surfaces them.
- **No soft deletes** unless an audit requirement forces it. Use status fields for state, not deletion masks.
- **Server time is authoritative.** Use `now() AT TIME ZONE 'Asia/Ho_Chi_Minh'` for any business cutoff (e.g., the 18:00 rule).

## Server-Enforced Business Logic

These rules **must run server-side** (Postgres function, trigger, or Supabase Edge Function). Client enforcement alone is unacceptable:

| Rule | Enforcement |
|---|---|
| Delivery date = N+1 if `submitted_at < 18:00 ICT`, else N+2 | DB trigger on `bookings` insert |
| Booking code generation (uniqueness, format) | DB function on insert |
| Daily 20,000-unit capacity cap | RPC checked when reviewer confirms an item |
| Supplier code must exist and be active | FK + RLS / RPC validation |
| VAT invoice mandatory on 1st delivery round | Check constraint on `booking_items` |
| Time slot must be one of the 4 fixed values | Enum |

## Validation Rules

| Field | Rule |
|---|---|
| Supplier Code | Must exist in `suppliers` and `active = true` |
| Number of POs | Integer 1–99 |
| Product Code / Process Code | Required, free text, max 100 chars each |
| Delivery Round | Integer ≥ 1; "cuối" (final) stored as a flag, not a sentinel value |
| VAT Invoice Photo | Required iff `delivery_round = 1` |
| Delivery Slip Photos | At least 1 per PO row; max 10 per row |
| Quantity (boxes/cartons) | Integer ≥ 1 |
| Time Slot | One of the 4 enum values |
| File types | jpg, jpeg, png, pdf |
| File size | ≤ 10 MB per file (configurable) |

## Security

- **RLS-first.** No table query bypasses RLS. The service role key never reaches the client.
- **Public booking submission is public.** Suppliers are not authenticated end-users; the form is open. To compensate:
  - Bookings are scoped by supplier code (must exist and be active)
  - Submission rate-limited per IP (Edge Function or Cloud Run middleware)
  - Booking detail URLs use **opaque tokens**, not the booking code, so QR scans don't allow enumeration
  - CAPTCHA on submission is **TBD** — open question
- **Staff and Manager log in** via Supabase Auth (email + password). Roles assigned in a `staff` table, mirrored to JWT claims via Supabase Auth hook.
- **File uploads** validated server-side: MIME sniff (not extension), size cap, virus scan (TBD).
- **No secrets in the repo.** Only `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` ship to the client. Service role key lives in Cloud Run secret manager.

---

## Performance

- **Pagination on every table.** Default 50 rows; max 200.
- **Image uploads go directly to Supabase Storage** — never base64-encoded into table columns.
- **Heavy queries (manager reports) use Postgres views or RPCs** — not N+1 client joins.
- **No realtime subscriptions in v1.** Polling on a 30s interval is acceptable for the reviewer dashboard. Add realtime later if it materially helps.

---

## Error Handling

- **Trust the framework and DB at internal boundaries.** Don't add defensive `try/catch` around code that already throws meaningful errors.
- **Validate at system edges only:** form submission, file upload, RPC inputs.
- **User-visible errors are Vietnamese.** Technical errors (logged) are English.
- **Failed Supabase calls** surface a toast with a friendly message and log full detail to the console (dev) / monitoring (prod).
- **Optimistic UI** is allowed for non-critical actions (e.g., toggling a row's expanded state); not for anything writing to DB.

---

## Testing

- **Unit tests** for: date logic, booking code generation, validation schemas, server-side capacity check.
- **Component tests** for: BookingForm (Zod schema integration), PO row dynamic rendering, VAT invoice conditional field.
- **E2E smoke** (Playwright): supplier submits a booking → reviewer confirms → receiver scans → reads back. One green path, no exhaustive edge-case coverage.
- **No mocked Supabase** in integration tests — point at a Supabase **branch** (use `mcp__supabase-mcp-server__create_branch`) so tests hit a real Postgres.
- Tests are not optional for new business logic.

---

## Process Rules (Non-Negotiable)

- A supplier delivering with **incorrect quantities** is still penalized for late delivery; the discrepancy is recorded.
- Receivers see **only confirmed PO items** when scanning. Rejected items are never shown at the gate.
- A **partially confirmed booking** retains its booking code; only confirmed items pass through receiving.
- **The 18:00 cutoff is server-enforced.** Client clock manipulation cannot shift delivery dates.

---

## Code Discipline

- **No comments unless the *why* is non-obvious.** Don't restate what code says.
- **No TODOs in committed code** — open an issue or remove the line.
- **No dead code, no commented-out blocks.**
- **One PR = one focused change.** No "while I'm in here" refactors mixed with feature work.
- **All PRs run lint + typecheck + tests in CI.** Failing CI blocks merge.
