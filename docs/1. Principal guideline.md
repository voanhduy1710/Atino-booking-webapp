# Principal Guidelines

Binding constraints for every implementation decision. If a requirement conflicts with these, raise it before coding.

---

## Architecture

- **Feature-based structure** — each feature is a self-contained module: `components/`, `hooks/`, `services/`, `types.ts`. New features can be added without touching unrelated ones.
- **No shared "ui" dumping ground.** Truly reusable primitives live in `src/shared/components/`. Anything used in only one feature stays inside that feature.
- **No barrel re-exports** that hide dependency trees. Import from concrete files.
- **One feature does not import from another feature's internals.** Cross-feature data goes through `shared/` or a documented service.

## Auth Rules

### Staff Accounts

- Stored in `AUTH_USERS` environment variable as JSON — **no database table** for staff credentials.
- Passwords hashed with **bcrypt** (cost 12). Never store or log plaintext.
- Login → Edge Function reads `AUTH_USERS`, runs `bcrypt.compare()`, returns **signed JWT (HS256)** containing `sub`, `role`, `allowedRoutes`, `exp`.
- JWT signed with `JWT_SECRET` environment variable. Expiry: 8 hours.
- JWT stored in **`localStorage`**. ⚠️ XSS risk — moving to `httpOnly` cookie is a P2 follow-up.
- Every protected Edge Function verifies `Authorization: Bearer <token>` before processing.

### Supplier Accounts

- Stored in the `supplier_accounts` Postgres table (see Architecture Overview).
- Registration is **open** — any supplier can fill the form.
- Account starts with `status = 'pending'`. Supplier cannot log in until admin approves.
- Admin approval links the account to a `supplier_id` in the `suppliers` table.
- Supplier JWT includes `supplier_id` — all booking queries are automatically scoped to this supplier.

### Admin Page

- `/admin` is client-side guarded only (JWT role check in `RequireRole.tsx`).
- No server-side backend guard on this route by design (internal tool only).
- Only the `admin` role reaches this page.

## Frontend Rules

- **Vietnamese UI. English code.** All user-visible strings are Vietnamese. All identifiers, comments, and commit messages are English.
- **No hardcoded warehouse names, supplier codes, or product codes** — these come from the DB.
- **Forms are server-validated.** Client Zod validation is UX only; Edge Functions are the source of truth.
- **Dynamic PO rows** via `useFieldArray` (React Hook Form). Reducing row count must confirm before discarding entered data.
- **The VAT invoice field appears inline in its PO row**, only when `delivery_round = 1`.
- **Photos upload immediately on file selection** (to a temp storage path), with per-file progress and retry.
- **Ghi chú** (supplier note) is a free-text textarea — always shown in the form, optional.
- **No inline `<style>` blocks.** Tailwind only.
- **Time zone:** all date math uses `Asia/Ho_Chi_Minh` via `date-fns-tz`. Never use `new Date()` for business logic without explicit zone.

---

## Database Rules

- **All schema changes go through migration files** applied via `mcp__supabase-mcp-server__apply_migration`. No undocumented dashboard edits.
- **RLS enabled on every table from day one.** Every table has explicit policies per role (see Architecture Overview).
- **Foreign keys are explicit and indexed.** No orphan rows.
- **Enums are Postgres enums** — not text check constraints — so TypeScript type generation surfaces them.
- **No soft deletes** unless audit requires it.
- **Server time is authoritative:** use `now() AT TIME ZONE 'Asia/Ho_Chi_Minh'` for the 18:00 delivery-date cutoff — never trust the client clock.
- **Data is retained indefinitely.** No automatic purge of booking records.

## Booking Code Format

`{YYYY-MM-DD}-{supplier_code}-{7-digit-number}`

Example: `2026-05-04-GC01-3434657`

- YYYY-MM-DD prefix → lexicographic sort = chronological sort (sortable in exports and DB)
- Supplier code in the middle → immediately identifies which supplier
- 7-digit number → random, collision-checked at insert
- Format is human-readable at the warehouse gate

## Server-Enforced Business Logic

These rules run in Postgres triggers or Edge Functions. Client enforcement is UX only:

| Rule | Enforcement |
|---|---|
| Delivery date = N+1 if before 18:00 ICT, else N+2 | DB trigger `set_booking_delivery_date` |
| Booking code generation (format + uniqueness) | DB trigger `generate_booking_code` |
| VAT invoice mandatory on delivery round 1 | DB check constraint on `booking_items` |
| Supplier must have `status = 'active'` | Edge Function verifies JWT `supplier_id` against DB |
| Booking status state machine transitions | RPC `transition_booking_status` |

**No daily capacity cap.** The reviewer decides case-by-case which PO items to confirm — the system imposes no automatic unit limit.

## Notification Rules

All notifications are in-app (bell icon). No email/SMS in v1.

| Event | Who gets notified |
|---|---|
| New booking submitted | Reviewer (`lethientinh`) |
| Booking item confirmed or rejected | Supplier (account owner) |
| Booking received | Supplier, Manager |
| Discrepancy recorded | Manager |
| Supplier account pending | Admin |
| Supplier account approved or rejected | Supplier |
| Amendment request submitted | Reviewer |
| Amendment approved or denied | Supplier |

Notifications are stored in the `notifications` table and fetched per recipient via `recipient_id`.

## Security

- Service role key never reaches the browser — lives only in Cloud Run environment variables, used only in Edge Functions.
- Supplier-scoped queries: supplier's `supplier_id` comes from the JWT, not from the request body. The frontend cannot fake a different supplier's scope.
- File uploads validated server-side: MIME type sniffed (not extension), size cap enforced.
- Rate limiting on `auth/login` and `finalize_booking` Edge Functions (per IP).
- Admin page: client-side role check only — acceptable for an internal tool; no sensitive data write operations should be possible without server JWT verification.

---

## Error Handling

- **User-visible errors are Vietnamese.** Technical errors (logged) are English.
- **Known errors** (invalid supplier code, capacity exceeded, wrong booking status) return structured codes from Edge Functions; UI maps code → Vietnamese message.
- **Generic 5xx:** show toast "Có lỗi xảy ra, vui lòng thử lại" and preserve form state.
- **Don't silence errors with empty catch blocks.** Surface them.

## Testing

- **Unit:** date logic, booking code generation, Zod schemas, RPC boundary conditions.
- **Component:** BookingForm dynamic row rendering, VAT field conditional, RequireRole guard.
- **E2E (Playwright):** full happy path — register → admin approves → login → submit booking → reviewer confirms → receiver scans → booking received.
- Integration tests point at a **Supabase branch** (`create_branch` MCP tool) — not the production project.
- Tests are not optional for new business logic.

## Image Storage Rules

- Photos stored in Supabase Storage bucket `booking-attachments` (private).
- Final path: `/{booking_id}/{item_id}/{filename}`
- Temp path: `/temp/{session_id}/{filename}` — cleaned up hourly by cron Edge Function.
- Images are never base64-encoded into DB columns.
- When Supabase Storage approaches capacity limits, migrate to **Google Cloud Storage** (same GCP project as Cloud Run). The `storage_path` column in `booking_item_photos` stores the path regardless of backend — a thin URL resolver handles signed URL generation for both.
- Signed URLs expire after 1 hour. Never expose raw bucket credentials to the frontend.
