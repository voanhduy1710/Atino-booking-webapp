## Decision Log

### Q1 — Supplier Authentication
**Decision (2026-05-09):** Suppliers must register an account (username + password + supplier code). Admin confirms registration and links to the `supplier_id`. No anonymous form submission. Viewing past bookings is per-account.

### Q2 — Master Data Sync
**Decision (2026-05-09):** Supplier master data is entered manually by the admin via the `/admin` → Nhà cung cấp tab. Supplier registration requests their supplier code; admin approves and links. Product/process codes are free-text strings typed by the supplier — no master list validation in v1.

### Q3 — Booking Code Format
**Decision (2026-05-09):** Format: `{YYYY-MM-DD}-{supplier_code}-{7-digit-random}`. Example: `2026-05-04-GC01-3434657`. YYYY-MM-DD prefix ensures lexicographic sort = chronological sort. Generated by DB trigger; collision-checked.

### Q4 — Daily 20,000-unit Capacity Cap
**Decision (2026-05-09):** No hard cap enforced by the system. The 20,000 figure was an example only. Reviewer decides case-by-case which PO items to confirm. Capacity view (daily confirmed units) is shown on the reviewer dashboard for situational awareness only.

### Q5 — Reviewer Validation Criteria (colors / sizes / 800 per color)
**Decision (2026-05-09):** Manual judgment by the reviewer only. The system does not enforce these criteria. Color, size, and unit-per-color fields are not in the schema.

### Q6 — Rejection Reason & Supplier Notification
**Decision (2026-05-09):** Reviewer inputs free-text reason when rejecting. Supplier receives an in-app notification with the reason. Notification bell + panel shown on all authenticated pages. Stored in `notifications` table.

### Q7 — Weekend / Holiday Handling
**Decision (2026-05-09):** N+1 / N+2 are calendar days only. No business-day arithmetic. No holiday calendar.

### Q8 — Partial Receive Across Multiple Visits
**Decision (2026-05-09):** Not supported in v1. One booking = one receiving event. The booking moves to `received` on a single submission by the receiver.

### Q9 — Discrepancy Logging
**Decision (2026-05-09):** Discrepancies are recorded in `discrepancy_log` table (quantity_booked vs quantity_received, difference). Visible in the manager dashboard. Supplier remains penalized per Atino policy.

### Q10 — Manager Reporting
**Decision (2026-05-09):** Native reports tab inside the manager dashboard (no Power BI). Shows: status summary tiles, all-bookings table with filters, discrepancy alerts, CSV export. Data retained indefinitely.

### Q11 — Notifications
**Decision (2026-05-09):** In-app notification system (bell icon + panel). No email/SMS in v1. Stored in `notifications` table. Events covered: booking submitted, confirmed, rejected, received, discrepancy, account pending/approved/rejected, amendment requested/resolved.

### Q12 — CAPTCHA
**Decision (2026-05-09):** No CAPTCHA. Rate limiting on Edge Functions per IP only.

### Q13 — File Types and Retention
**Decision (2026-05-09):** Accepted types: jpg, jpeg, png, pdf. Max 10 MB per file. Delivery slip photos are operational evidence and retained. When Supabase Storage capacity becomes a concern, migrate to Google Cloud Storage (same GCP project). No automatic deletion of booking photos in v1.

### Q14 — Multiple Warehouses
**Decision (2026-05-09):** Single warehouse in v1 (Kho Tân Hoàng Long). Expandable via `warehouses` table — admin adds new warehouses without code changes.

### Q15 — Booking Edits / Amendments
**Decision (2026-05-09):** Supplier cannot edit a submitted booking directly. Instead, they can submit an amendment request (with a note). The reviewer confirms or denies the request. The system does not automatically apply the amendment — it signals intent; manual follow-up happens outside the system for v1.

### Q16 — Receiver Discrepancy Photos
**Decision (2026-05-09):** Yes — receiver can upload photos during the receiving flow. Stored in `booking_item_photos` with `photo_type = 'discrepancy'`.

### Q17 — Audit Log
**Decision (2026-05-09):** Yes — implement a full audit trail. `confirmed_by` / `confirmed_at`, `received_by` / `received_at` on bookings; `reject_reason` on items; `discrepancy_log` table; `booking_amendments` table. Sufficient for v1 compliance. A full row-level diff audit log is a future enhancement if needed.

### Q18 — Test Data Strategy
**Decision (2026-05-09):** Use Supabase branches (`create_branch` MCP tool) for integration tests. Tests point at the branch, not the production project.
