# Open Questions

Questions that affect implementation but haven't been answered yet. Each item lists what we assumed in the design and what to verify with the stakeholder before coding the relevant phase.

Order roughly tracks the implementation phases — top items block earlier work.

---

## Blocking — Resolve Before Phase 2

### Q1. Supplier authentication

**Assumption:** The booking form is **public** (no supplier login). Suppliers are identified by selecting their `Mã NCC` from a dropdown.

**Why we assumed this:**
- The reference (AEON) uses a public token-based form
- The brief said "any user would be able to register to deliver"
- No login screen appears in the design mockups

**Need to confirm:**
- Is anyone allowed to submit a booking on behalf of any supplier code?
- If yes — do we need CAPTCHA or another anti-abuse measure?
- If no — should suppliers receive a credential (email/SMS magic link) or use a shared password?

---

### Q2. Master data sync

**Assumption:** Supplier and product master data is **seeded manually** in Phase 1 and refreshed by an admin user (no automatic sync from finance).

**Need to confirm:**
- Is there an existing API or export from the finance/accounting system to sync `suppliers`?
- How often does the supplier list change? (frequency drives whether we need automation or a CSV import is enough)
- Same question for product / process codes — are these from another master list, or free text per booking?

---

### Q3. Booking code format

**Assumption:** 14-digit numeric code, mirroring the AEON example `80072601100032`. Generated by a DB sequence + check digit (or simple monotonic + random).

**Need to confirm:**
- Does the code need a specific format (date prefix, supplier prefix)?
- Is it human-typed at the warehouse gate? (drives length / typeability)
- Should it embed any meaning (e.g., delivery date prefix)?

---

### Q4. Daily 20,000-unit cap — interpretation

**Assumption:** "20,000 hàng/ngày" is a single warehouse-wide cap on **confirmed `quantity_booked` per `delivery_date`**. Once reached, no further item confirmations for that date.

**Need to confirm:**
- Is it 20,000 cartons (kiện/thùng) or 20,000 individual units?
- Is the cap per-supplier or warehouse-wide?
- Is the cap a hard limit or a soft target the reviewer can override?
- Does it apply to total booked, total confirmed, or total received?

## Resolve Before Phase 3

### Q5. Reviewer rules: full colors / sizes / 800 per color

**Quote from spec:** "Phiếu giao lần 1, 2 - Yêu cầu đủ màu, đủ size. Tối thiểu 800 hàng/màu"

**Assumption:** This is **manual judgment** by the reviewer — the system doesn't enforce it (we don't have color/size in the schema today).

**Need to confirm:**
- Should color and size be structured fields on `booking_items`?
- Should the system enforce the 800-per-color minimum?
- Or is this purely a checklist for the human reviewer?

---

### Q6. Reject reason workflow

**Assumption:** When rejecting an item, the reviewer must enter a free-text reason. The supplier sees the reason on the booking detail page.

**Need to confirm:**
- Is there a fixed list of rejection reasons to choose from?
- How is the supplier notified of rejection? (Today: only by checking the URL — see Q11)

---

### Q7. Weekend / holiday handling

**Assumption:** N+1 / N+2 are calendar days, including weekends and holidays.

**Need to confirm:**
- Does the warehouse operate on weekends?
- Should N+1 skip non-working days (i.e., business-day arithmetic)?
- Is there a holiday calendar maintained somewhere?

---

## Resolve Before Phase 4

### Q8. Receiver flow: partial receive

**Assumption:** A receiver records all confirmed PO items in a single submission. Once submitted, booking → `received` and is locked.

**Need to confirm:**
- Can a single booking be received across multiple visits (e.g., delivered in two trips)?
- If so, do we need a separate `delivery_event` table?

---

### Q9. Discrepancy logging

**Assumption:** When `quantity_received` ≠ `quantity_booked`, the difference is implicit (computed). No separate "penalty" record is created.

**Need to confirm:**
- Is there a separate penalty / non-compliance workflow we need to record?
- Who consumes the discrepancy data? (manager dashboard, finance system, both?)

---

## Resolve Before Phase 5 / 6

### Q10. Manager reporting needs

**Assumption:** Manager dashboard shows: all-bookings table, daily capacity, status summary tiles, CSV export.

**Need to confirm:**
- Are there specific KPIs/metrics the manager checks daily?
- Is Power BI integration still on the table or fully descoped? (User said "no" to a dedicated Power BI doc — confirming descope.)
- Date range for historical retention? (1 year? 3 years? indefinite?)

---

### Q11. Notifications

**Assumption:** No notifications in v1. Supplier checks the booking URL to see status updates.

**Need to confirm:**
- Email or SMS notification on confirm/reject/received?
- Reminder to receiver before a booking's time slot?
- Daily digest to manager?

---

### Q12. CAPTCHA / abuse prevention

**Assumption:** IP-based rate limiting on the public booking submission. No CAPTCHA in v1.

**Need to confirm:**
- Comfortable with rate-limit-only, or do we add reCAPTCHA / Turnstile from the start?

## Lower Priority

### Q13. File size and types

**Assumption:** Max 10 MB per file; types: jpg, jpeg, png, pdf.

**Need to confirm:** Acceptable, or different limits?

### Q14. Multiple warehouses

**Assumption:** Only one warehouse for v1: `Kho Tân Hoàng Long`. The schema includes a `warehouse` field for forward compatibility but is not user-selectable.

**Need to confirm:** Will more warehouses come online soon? (drives whether we make this configurable now or later.)

### Q15. Booking edits / amendments

**Assumption:** A submitted booking cannot be edited by the supplier. They must wait for review or resubmit a new booking.

**Need to confirm:** Is post-submit edit needed? (e.g., before reviewer acts.)

### Q16. Receiving discrepancy media

**Assumption:** Receiver may add notes, but no photo capture during receive in v1.

**Need to confirm:** Should receiver upload photos of damaged goods or discrepancies?

### Q17. Audit log

**Assumption:** No dedicated audit log table; status fields and `*_by`/`*_at` columns provide minimal trail.

**Need to confirm:** Is a full audit log (who-did-what-when, with diffs) required for compliance?

### Q18. Test data strategy

**Assumption:** Use a Supabase **branch** for integration tests (`mcp__supabase-mcp-server__create_branch`).

**Need to confirm:** Acceptable, or do we need a separate fully-isolated dev project?
