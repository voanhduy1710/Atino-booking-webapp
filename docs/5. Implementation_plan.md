# Implementation Plan

Phased rollout from empty repo to production-deployed app. Each phase has a clear scope, deliverables, and acceptance criteria. Move to the next phase only when the previous one is green.

Estimates assume one engineer working alongside the AI agent. Adjust as needed.

## Phase 2 — Public Supplier Booking Flow (2 days)

**Goal:** A supplier can submit a booking end-to-end and see the QR confirmation screen.

### Tasks
1. **Landing page** (`features/home/components/LandingPage.tsx`)
   - 3 buttons per design mockup
   - Black/white palette
   - Atino logo (use `Atino Logo.svg`)
2. **Static guide pages** (`features/home/components/GuideCreate.tsx`, `GuideReceiving.tsx`)
   - Pull content from `business logic/excel file content.md` and screenshots from `business logic/*.png`
3. **Booking form** (`features/booking/`)
   - `BookingForm.tsx` orchestrating Sections I and II
   - `SupplierSection.tsx` (dropdown + name lookup)
   - Delivery date preview (client-side display only)
   - `PoTable.tsx` rendering `useFieldArray` rows via TanStack Table
   - `PoRow.tsx` with inline VAT invoice on round=1
   - `TimeSlotPicker.tsx`
   - `DeliveryNote.tsx` with pre-filled standard text
4. **Zod schema** (`features/booking/schemas.ts`) mirroring server validation
5. **File upload** (`shared/components/FileUpload.tsx`)
   - Direct-to-storage at temp path
   - Progress, retry, remove
6. **Submission** wires up to `finalize_booking` Edge Function
7. **Confirmation screen** (`BookingConfirmation.tsx`)
   - Big QR (qrcode.react)
   - Booking code text
   - Print-friendly layout
8. **Routing** for `/`, `/booking/new`, `/booking/:token/confirmation`, `/guide/*`

### Tests
- Unit: Zod schema rejects invalid input (missing VAT on round=1, etc.)
- Unit: delivery date preview helper for both before/after 18:00 ICT
- Component: PoRow conditionally renders VAT field
- Component: BookingForm submission disabled while uploads pending
- Playwright smoke: landing → form → submit → confirmation visible

### Acceptance
- A real submission inserts rows into `bookings`, `booking_items`, `booking_item_photos`
- Delivery date is correctly N+1 / N+2 in ICT
- Booking code is 14 digits and unique
- QR code resolves to a valid booking detail URL
- Storage files are moved from `/temp/...` to final paths
- Smoke test green in CI

## Phase 3 — Reviewer Dashboard (1 day)

**Goal:** Reviewer can log in, see pending bookings, confirm/reject items, with capacity enforcement.

### Tasks
1. **Login page** (`features/auth/components/LoginForm.tsx`)
2. **Route guard** (`features/auth/guard/RequireRole.tsx`)
3. **Pending bookings list** (`features/warehouse/reviewer/`)
   - TanStack Table: booking_code, supplier_name, delivery_date, time_slot, item_count, submitted_at
   - Polling every 30s
   - Filter by delivery_date
4. **Booking review modal** (`BookingReviewModal.tsx`)
   - PO list with thumbnails (signed URLs)
   - Per-item Confirm / Reject buttons
   - Reject reason input
5. **Confirm action** calls `confirm_booking_item` RPC
   - Surface capacity-exceeded error gracefully
6. **Reject action** calls `reject_booking_item` RPC with reason
7. **Auto-finalize** booking status when all items resolved (via `transition_booking_status`)
8. **Daily capacity widget** for next 7 days

### Tests
- Unit: capacity check RPC (insert seed data → confirm at boundary)
- Component: review modal renders and dispatches actions
- E2E (Playwright): submit → log in as reviewer → confirm one item → booking moves to confirmed

### Acceptance
- Reviewer dashboard shows live pending bookings
- Confirm respects 20,000 cap; UI shows error on exceed
- Partial confirmation correctly updates booking status to `confirmed`
- Full rejection moves booking to `rejected`

## Phase 4 — Receiver Scan Flow (1 day)

**Goal:** Receiver scans QR (or types code), sees only confirmed items, records actuals.

### Tasks
1. **Receiver page** (`features/warehouse/receiver/`)
2. **QR scanner component** (`QrScanner.tsx`) using `@zxing/browser`
   - Camera permission UX
   - Fallback to manual code input
3. **Booking lookup** by token (or code) → render `BookingScanResult`
4. **State guards**:
   - `pending` → "chưa xác nhận"
   - `rejected` → "không hợp lệ"
   - `received` → "đã nhận trước đó"
   - `confirmed` → render receive form
5. **Receive form** (`ReceiveForm.tsx`) — quantity inputs per confirmed item
6. **Submit** calls `receive_booking` RPC
7. Success summary screen with discrepancy notes

### Tests
- Unit: each booking status maps to expected receiver UI state
- E2E: scan flow (mocked camera) end-to-end

### Acceptance
- Scanning a confirmed booking shows ONLY confirmed items
- Scanning a rejected/pending booking shows the right error message
- Submitting receive moves booking to `received` and stores quantities

- Realtime subscriptions
- Mobile-native app (web is responsive-first)

## Risk Register

| Risk | Mitigation |
|---|---|
| Supplier master data sync (source = finance) | Phase 1 seeds manually; Open Question for long-term sync mechanism |
| Camera-based QR scanning unreliable on warehouse hardware | Always provide manual code input as fallback |
| 20,000 cap interpretation may differ from intent | Validate with reviewer (Lê Thiên Tình) early in Phase 3 |
| 18:00 cutoff edge cases (server clock drift) | Use `now() AT TIME ZONE 'Asia/Ho_Chi_Minh'` in Postgres — single source of truth |
| File upload size on slow Vietnamese mobile networks | 10 MB cap; per-file progress; resumable uploads if needed (Supabase Storage supports tus) |
| Public submission abuse / spam | Rate limit + future CAPTCHA (Open Question) |
